Erro de CORS no navegador: como resolver no Node.js e Nginx sem usar wildcard (*)

Recebeu a mensagem "Access to fetch at... has been blocked by CORS policy"? Entenda por que o erro acontece e aprenda a configurar Node.js, Nginx e Next.js com suporte a cookies/sessão sem abrir brechas de segurança nem ter problemas de cache com CDN.

Publicado em 01 de setembro de 2026 · 6 min de leitura

Você faz um deploy, abre o frontend e a aplicação não carrega dados: o console do navegador é inundado com o erro Access to fetch at 'https://api.seusite.com' from origin 'https://seusite.com' has been blocked by CORS policy. Na pressa de destravar o sistema, a reação mais comum é adicionar Access-Control-Allow-Origin: * — o que quebra requisições com cookies/sessão (credentials: 'include') ou escancara sua API para qualquer site na internet. Resolver CORS de forma definitiva exige entender o que o navegador está pedindo, configurar uma allowlist dinâmica e instruir caches com Vary: Origin.

Por que o erro de CORS acontece

O CORS (Cross-Origin Resource Sharing) é uma restrição imposta pelo navegador, não pelo servidor. Quando o JavaScript do seu frontend (ex.: https://app.seusite.com) tenta fazer uma requisição para uma API em domínio, subdomínio ou porta diferente (ex.: https://api.seusite.com), o navegador bloqueia a leitura da resposta a menos que a API confirme explicitamente que aquela origem é autorizada.

Em requisições que usam métodos como PUT, DELETE, PATCH ou enviam cabeçalhos customizados (como Authorization ou Content-Type: application/json), o navegador envia primeiro uma requisição prévia chamada preflight (OPTIONS). Se o servidor não responder a essa requisição OPTIONS com status 204/200 e os headers corretos, a requisição principal nem chega a ser enviada.

Como resolver no Node.js (Express)

Para suportar autenticação com cookies ou tokens via header sem usar wildcard *, implemente uma allowlist dinâmica e inclua o header Vary: Origin para evitar que CDNs entreguem respostas cacheadas para a origem errada:

const express = require('express');
const cors = require('cors');
const app = express();

// Lista explícita de domínios autorizados
const origensPermitidas = [
  'https://seusite.com',
  'https://www.seusite.com',
  'https://app.seusite.com',
  'http://localhost:3000' // apenas em desenvolvimento
];

const corsOptions = {
  origin: (origin, callback) => {
    // Permite requisições sem origin (mobile apps, curl ou tarefas cron)
    if (!origin || origensPermitidas.includes(origin)) {
      callback(null, true);
    } else {
      callback(new Error('Bloqueado pela política de CORS da VulnexusAI'));
    }
  },
  credentials: true, // Permite envio de cookies e tokens de sessão
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE', 'OPTIONS'],
  allowedHeaders: ['Content-Type', 'Authorization', 'X-Requested-With'],
  maxAge: 86400 // Cache do preflight por 24 horas no navegador
};

// Garante que CDNs criem entradas de cache separadas por origem
app.use((req, res, next) => {
  res.header('Vary', 'Origin');
  next();
});

app.use(cors(corsOptions));
// Responde imediatamente a qualquer preflight OPTIONS
app.options('*', cors(corsOptions));

Como resolver no Nginx (Reverse Proxy)

No Nginx, o padrão mais limpo e seguro mapeia as origens válidas via map fora do bloco de rotas, devolvendo 204 no preflight OPTIONS e anexando Vary: Origin:

# 1. Allowlist dinâmica fora do bloco server
map $http_origin $cors_origin {
    default "";
    "https://seusite.com" "$http_origin";
    "https://app.seusite.com" "$http_origin";
    "http://localhost:3000" "$http_origin";
}

# 2. Habilita credenciais somente se a origem foi validada na lista
map $cors_origin $cors_cred {
    default "";
    "~^https?://" "true";
}

server {
    listen 443 ssl http2;
    server_name api.seusite.com;

    location / {
        # Preflight OPTIONS com saída limpa
        if ($request_method = 'OPTIONS') {
            add_header 'Access-Control-Allow-Origin' $cors_origin always;
            add_header 'Access-Control-Allow-Credentials' $cors_cred always;
            add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, PATCH, DELETE, OPTIONS' always;
            add_header 'Access-Control-Allow-Headers' 'Content-Type, Authorization, X-Requested-With' always;
            add_header 'Access-Control-Max-Age' 86400 always;
            add_header 'Vary' 'Origin' always;
            add_header 'Content-Type' 'text/plain; charset=utf-8';
            add_header 'Content-Length' 0;
            return 204;
        }

        # Headers nas requisições reais (GET, POST, etc.)
        add_header 'Access-Control-Allow-Origin' $cors_origin always;
        add_header 'Access-Control-Allow-Credentials' $cors_cred always;
        add_header 'Vary' 'Origin' always;

        proxy_pass http://127.0.0.1:4000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Como resolver no Next.js (App Router Route Handler)

Para rotas de API no Next.js (app/api/[...]/route.ts), use uma função utilitária com lógica condicional de origem similar ao Express:

import { NextRequest, NextResponse } from 'next/server';

const origensPermitidas = [
  'https://seusite.com',
  'https://app.seusite.com',
  'http://localhost:3000',
];

function getCorsHeaders(request: NextRequest) {
  const origin = request.headers.get('origin') ?? '';
  const isPermitida = origensPermitidas.includes(origin);

  const headers = new Headers();
  if (isPermitida) {
    headers.set('Access-Control-Allow-Origin', origin);
    headers.set('Access-Control-Allow-Credentials', 'true');
  }
  // Fundamental para evitar respostas erradas cacheadas em edge/CDN
  headers.set('Vary', 'Origin');
  headers.set('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE, OPTIONS');
  headers.set('Access-Control-Allow-Headers', 'Content-Type, Authorization');
  headers.set('Access-Control-Max-Age', '86400');

  return headers;
}

// Resposta para preflight OPTIONS
export async function OPTIONS(request: NextRequest) {
  return new NextResponse(null, {
    status: 204,
    headers: getCorsHeaders(request),
  });
}

// Handler GET / POST de exemplo
export async function GET(request: NextRequest) {
  const headers = getCorsHeaders(request);
  return NextResponse.json({ status: 'ok', data: 'Dados protegidos' }, { headers });
}

Erros comuns que quebram a produção

  • Esquecer o cabeçalho Vary: Origin: Quando você reflete a origem dinamicamente a partir de uma allowlist, CDNs e proxies intermediários (Cloudflare, Varnish, Fastly) podem armazenar em cache a resposta gerada para o site-a.com e servi-la para o site-b.com. O navegador no site-b.com verá a origem trocada e bloqueará a requisição. O Vary: Origin obriga a CDN a criar chaves de cache isoladas por origem.
  • Usar * junto com credentials: 'true': A especificação W3C proíbe essa combinação. Se o backend responder Access-Control-Allow-Origin: * para uma chamada com cookies/sessão, o navegador rejeitará a resposta no lado do cliente.
  • Refletir cegamente qualquer Origin: Fazer res.setHeader('Access-Control-Allow-Origin', req.headers.origin) sem validar em uma lista autorizada permite que qualquer site malicioso faça requisições autenticadas contra a sua API.
  • Esquecer de responder ao método OPTIONS: Se o servidor retornar 404, 401 ou 500 para a requisição de preflight, o navegador aborta e nunca envia a requisição principal.
  • Duplicação de cabeçalhos (Backend + Nginx): Se o Express e o Nginx adicionarem o header ao mesmo tempo, o navegador receberá valores duplicados (ex.: https://seusite.com, https://seusite.com) e abortará o carregamento por erro de parsing.
